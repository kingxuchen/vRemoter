# 通用语音输入：语音目标解耦与可录制语音触发键

> 状态：待评审 · 目标应用：任意语音输入法（豆包输入法降级为默认项）
> 关联产品上下文：PRODUCT.md · 现有已发布版本 1.1.1

---

## Problem Statement

用户用 vRemoter 让蓝牙语音遥控器（X6-Remote、Chromecast Voice Remote）给 Mac 做语音输入。遥控器的麦克风本来就能通过 ATVV 私有协议被 vRemoter 主动打开，经 ADPCM 解码后与 MacBook 内置麦克风混合，送进一个名为 `vRemoteDr 2ch` 的 CoreAudio 输入设备。但这套能力**只能用豆包输入法**。

原因是会话状态机把「豆包输入法进程是否正在录音」当成了唯一真相来源。它通过一个硬编码的豆包 bundle ID 绑定豆包的 CoreAudio 进程，监听该进程是否在采集输入。豆包不录音、没运行、或换成了别的软件，状态机就判定会话无效，**立刻关闭遥控器麦克风**。于是用户按下语音键时，遥控器麦克风根本不会打开，Mac 里一片安静。

用户实际的需求是把遥控器变成一个通用遥控麦克风：按键激活后正常收音，把音源送进 Mac，最终交付给任意语音输入法——比如用户电脑里的 Type4Me。这半条通路其实**已经具备**，Type4Me 明确支持在设置里按优先级指定多个输入设备，用户只要把 `vRemoteDr 2ch` 加进去就能拿到混音。缺的是会话状态机与语音目标之间的耦合。

同时还有一个独立缺陷：**语音键发哪个快捷键是写死的**。现有实现是一个包含 Option / Command / Control / Shift / Fn 五项的固定枚举，用户只能从这五个里挑一个。更糟的是这份枚举同时保存了左右两个键码，而取值时用 `min()` 选主键码，导致永远发出左 Control，右 Control（Type4Me 的默认触发键）根本发不出去。

用户明确反对由 vRemoter 替用户猜快捷键：**不同应用、每个用户设置的激活快捷键都不同，vRemoter 不可能知道其他应用用哪个键**。所以快捷键必须完全由用户自行指定。

---

## Solution

**一、语音目标解耦。** 遥控器麦克风的开关不再由任何特定语音输入法的进程状态驱动，改由 vRemoter 自己持有语音会话：按下语音键就打开遥控器麦克风、开始双麦混合，并发送一次用户配置的快捷键；再按一下就再发一次快捷键并关闭遥控器麦克风。任何能够选择输入设备的软件都可以消费这份音源，豆包输入法不再是特例，只是默认项。麦克风混音逻辑、双麦配置、遥控器按键映射、虚拟音频驱动全部保持不变。

**二、快捷键完全交给用户。** 删除固定枚举，改为记录一个 `(keyCode, modifierFlags)` 的快捷键值。设置里提供一个录制式拾取控件：点击进入拾取状态，用户直接按下想要的组合键，设置项回显结果。支持任意组合，包括带普通主键的组合，不再局限于无修饰键的单键。**代码中不内置任何默认快捷键。**

**三、安全网。** 关闭遥控器麦克风之前先确认没有程序仍在占用 `vRemoteDr 2ch`。这道检查只在语音会话进行期间生效，并排除 vRemoter 自身进程。它防止的是一个具体的失败：第二次快捷键被目标应用吞掉时，vRemoter 已经关闭麦克风而目标仍在录音，用户对着遥控器说话却录到静音。

**四、文案与指引。** 界面去除豆包专属措辞，改为通用的语音输入表述，并新增一条明确指引，告诉用户需要到目标语音输入应用自己的设置里，把 `vRemoteDr 2ch` 加入它的输入设备列表——否则配置正确也不会有声音。

## User Stories

### 通用语音目标（核心）

1. 作为使用 Type4Me 的用户，我希望按下遥控器语音键就能打开遥控器麦克风，这样我不用手伸向 MacBook 就能说话。
2. 作为使用 Type4Me 的用户，我希望遥控器的音源能被 Type4Me 录进去，这样我说话时它能识别出我的文字。
3. 作为使用 Type4Me 的用户，我希望完全不安装豆包输入法也能正常使用遥控器，这样我不会为了用麦克风被迫装一个不用的软件。
4. 作为使用 Type4Me 的用户，我希望再按一次语音键就停止录音并关闭遥控器麦克风，这样我不需要额外的关闭动作。
5. 作为使用 Type4Me 的用户，我希望按下语音键之后界面告诉我「正在录音」，这样我知道它听见了我的操作。
6. 作为使用 Type4Me 的用户，我希望停止之后界面回到待机状态，这样我知道麦克风已经关掉了。
7. 作为使用 Type4Me 的用户，我希望停止后遥控器麦克风确实被释放，这样它不会一直亮着耗电。
8. 作为使用 Type4Me 的用户，我希望同时连接 X6 和 Chromecast Remote 时，两者各自独立地开麦和关麦，这样一台没动不会影响另一台。
9. 作为使用 Type4Me 的用户，我希望遥控器麦克风的收音内容与豆包模式下**完全一致**（遥控器麦 + MacBook 麦等权混合），这样我换软件不用重新适应音质。
10. 作为使用 Type4Me 的用户，我希望在 Studio Mixer 里勾掉 MacBook 麦克风后 Type4Me 也只录到遥控器，这样我不会收到 MacBook 麦克风的环境噪音。
11. 作为使用 Type4Me 的用户，我希望目标应用没在运行时按下语音键不会让 vRemoter 出错或卡死，这样我可以先按再开应用。
12. 作为使用 Type4Me 的用户，我希望目标应用崩溃或被强制退出时，遥控器麦克风仍然被正确关闭，这样它不会变成一直开着的麦克风。

### 安全网

13. 作为用户，我希望按下停止时，如果还有程序正在占用 `vRemoteDr 2ch`，麦克风不会被直接切断，这样我对着遥控器说话不会录到一片死寂。
14. 作为用户，我希望这个占用检查只在录音期间进行，这样我把 `vRemoteDr 2ch` 设成系统默认麦克风后，vRemoter 不会因为菜单栏、Siri 之类常驻读取而永远不关麦。
15. 作为用户，我希望 vRemoter 自己的进程不被算作占用者，这样麦克风能正常关闭。
16. 作为用户，我希望在占用检查犹豫时界面告诉我发生了什么，这样我知道麦克风为什么还开着。

### 快捷键录制

17. 作为用户，我希望在设置里点一下就能进入「按下你要的快捷键」的拾取状态，这样我不必去查任何按键代码。
18. 作为使用 Type4Me 的用户，我希望录下**右 Control**，这样它和 Type4Me 的默认触发键一致，我不用去改 Type4Me 的设置。
19. 作为用户，我希望录下带普通主键的组合（例如 Option + 空格），这样那些用这种组合做语音触发的应用也能用。
20. 作为用户，我希望录下带两个修饰键的组合（例如 Control + Shift + V），这样组合键不再有上限。
21. 作为用户，我希望录完之后设置项回显成我能看懂的符号（例如「⌃ 右Control」），这样我知道录对没有。
22. 作为用户，我希望重新录制时能直接覆盖旧值，这样改设置不用先清空。
23. 作为用户，我希望录制框旁边有一个「清除」入口，这样我可以把语音键恢复成不发送任何快捷键。
24. 作为用户，我希望在拾取状态下按 Esc 能取消且不改动已保存的值，这样我误点了不会丢配置。
25. 作为用户，我希望拾取时不会把我正在输入的密码或其他内容录进去，这样隐私不受影响。
26. 作为用户，我希望录制好的快捷键被实际发送出去时与我录的一致，这样我不会录了 A 结果发成 B。

### 首次使用与存量兼容

27. 作为全新安装的用户，我希望语音键在设置之前完全不发任何快捷键、也不打开麦克风，这样 vRemoter 不会替我猜一个用不上的键。
28. 作为全新安装的用户，我希望界面明确提示「先设置你要触发的快捷键」，这样我知道为什么语音键还没反应。
29. 作为全新安装的用户，我希望有一个明显入口能直接跳到快捷键设置，这样我不必自己找。
30. 作为全新安装的用户，我希望在设置完成之前界面不出现误导性的「等待豆包输入法」之类的文案，这样我知道这是没配置而不是出错。
31. 作为 1.1.1 的豆包用户，我升级后语音键仍然按原来的方式工作，这样我不必重新配置。
32. 作为 1.1.1 的豆包用户，我如果曾经手动改过触发键，升级后那个设置仍然是我改过的值，这样我的配置不会被覆盖。
33. 作为 1.1.1 的豆包用户，我不希望升级需要卸载重装或重新安装驱动，这样我不必处理任何额外步骤。
34. 作为任意用户，我希望 `vRemoteDr 2ch` 这个设备名保持不变，这样我之前在别处保存过的输入设备选择仍然有效。

### 指引与文案

35. 作为用户，我希望界面告诉我「需要在你的语音输入应用里选择 `vRemoteDr 2ch` 作为输入设备」，这样我知道配好 vRemoter 后还要做一步。
36. 作为用户，我希望这段指引明确写出设备名，这样我能照着找。
37. 作为用户，我希望界面里不再出现豆包字样，这样它看起来是一个通用工具而不是某个软件的附属品。
38. 作为用户，我希望设置项的措辞不出现 bundle ID、keyCode、transport 这类开发者术语，这样我能看懂。

### 可访问性与质量

39. 作为使用 VoiceOver 的用户，我希望快捷键录制控件有明确的标签和朗读描述，这样我知道它做什么。
40. 作为使用 VoiceOver 的用户，我希望录音中和待命两种状态能被朗读区分，这样我知道当前状态。
41. 作为使用键盘的用户，我希望能用 Tab 和空格完成一次完整的快捷键录制，这样我不用鼠标。
42. 作为状态不能单靠颜色表达的用户，我希望录音状态同时有文字，这样我不用看颜色。
43. 作为开启了减弱动效的用户，我希望录制状态的切换不依赖动画，这样功能完整。
44. 作为用户，我希望最小窗口尺寸下快捷键设置项不被裁切，这样我能完整看到录制框和回显。

### 边界与失败

45. 作为用户，我希望语音键按住不放不会重复触发录音，这样长按不会产生混乱状态。
46. 作为用户，我希望快速连按两次语音键最终回到待机状态，这样误触不会卡在中间状态。
47. 作为用户，我希望遥控器断开连接时自动关闭麦克风并回到待机，这样麦克风不会因为断连而悬着。
48. 作为用户，我希望在目标应用录音期间切换到别的应用不会中断会话，这样我可以边写代码边口述。
49. 作为用户，我希望 vRemoter 自己的窗口不在前台时快捷键依然生效，这样它不抢焦点。
50. 作为用户，我希望录制到系统保留键（例如亮度、音量）时给我明确提示而不是静默失败，这样我知道为什么录了不生效。

## Implementation Decisions

### 会话真相的所有权转移

- **语音目标状态观察器的职责收窄。** 现有模块同时承担「绑定特定 bundle ID 的进程」「监听该进程是否采集输入」「发布状态快照」三件事。新形态下它只保留一件：回答「此刻有没有程序正在占用 `vRemoteDr 2ch`」。按 bundle ID 绑定进程的能力整块移除。
- **占用者查询走 CoreAudio 公共接口。** 枚举系统音频进程对象集合，取每个进程在输入作用域下打开的设备，判断是否包含 `vRemoteDr 2ch`。读取是一次查询，不建立长期监听。
- **会话协调器的驱动源从「快照回调」改为「语音键事件」。** 现有实现收到目标应用的状态快照后才推进会话阶段；新实现收到语音键事件即推进。原有的阶段机（open / opening / closing / closed）、generation 计数器、有限重试、开麦与关麦确认的框架保留并复用，只更换驱动它的信号。
- **注入契约保持不变。** 会话协调器今天已经把「设置路由开关」「发送触发」「取当前时间」「请求打开遥控器麦克风」「请求关闭遥控器麦克风」「提供首选遥控器」全部作为构造注入。新增的占用查询同样以注入形式接入，因此现有测试装配方式不受影响。
- **占用查询必须排除自身进程。** vRemoter 自身在该设备上挂有 IOProc，会把自己统计成占用者。

### 安全网的生效范围

- 占用查询**只在语音会话窗口内触发**，即从语音键按下到完成关闭之间。不做常驻监听，不在待命态轮询。
- 这条限定是必要的：如果 `vRemoteDr 2ch` 被设为系统默认输入，菜单栏、控制中心、Siri 等会持续持有它，无限定会让麦克风永远无法关闭，既是隐私问题也是耗电问题。
- 当检查判定「仍有占用者」时，关闭流程被推迟，并向界面发布一条可朗读的状态说明，推迟到何时结束需要一个明确的终止条件，不得形成无限等待。
- 关闭完成后追加一小段尾巴延迟再释放遥控器 ATVV 麦克风通道，用于覆盖目标应用按「松开结束」语义收尾的那一小段时间。这段尾巴独立于占用查询存在，作为补充而非替代。

### 快捷键值模型

- 引入一个表示快捷键的纯值类型，承载键码与修饰键标记两个分量。取代现有的固定枚举。
- 该类型提供三个纯函数：**从捕获到的按键事件构建**、**渲染为可读回显文本**、**渲染为合成事件描述**。三者均不触碰系统事件层，因此可直接测试。
- 实际的键盘事件投递通过可注入的发送器完成，使「发了几次、发的什么」可被断言。
- **合成任意组合的机制：** 把修饰键标记直接设置在主键事件上即可，无需真实投递各修饰键的按下与抬起。这与现有 Option 触发键的做法同构。
- **删除现有的枚举及其取值缺陷。** 当前枚举为每个概念同时保存左右两个键码再用 `min()` 取主键码，导致永远发左键码；值类型不保留这种一对多的表示，从结构上消除该缺陷。
- **代码中不内置任何默认快捷键。** 不存在「默认 Option」或任何其他预设。唯一的例外是存量迁移分支（见下）。

### 存量迁移

- 迁移判据分三种情形：
  1. 设置存储中存在旧触发键的字符串值 → 视为用户主动设置过，迁移为对应的键码与修饰键。
  2. 旧触发键的键不存在，但存在其他 vRemoter 设置 → 视为 1.1.1 的存量用户且从未碰过该下拉框，迁移为旧行为实际使用的那个键，保证升级后不失灵。
  3. 设置存储完全为空 → 视为全新安装，不迁移，语音键在配置前不响应。
- **第 2 条是推断，不是用户明确指定的要求。** 它存在的唯一理由是：旧版本的触发键下拉框默认值并不写入存储，所以绝大多数从未碰过它的存量用户会被第 3 条误判为全新安装而突然失灵。风险是该判据在极小概率下无法区分「装过但清过全部设置的用户」与「全新用户」，这种用户会被当作全新用户处理。实施时若发现判据不可靠，应停下向用户确认，不得静默改变行为。
- 迁移只做一次，迁移后写入新的值类型表示。

### 未配置状态的界面行为

- 语音键在未配置快捷键时**完全不响应**：不发送快捷键，也不打开遥控器麦克风。
- 理由：打开麦克风却没有任何应用在录音，只会让人误以为麦克风损坏。
- 界面显示明确的「先设置你要触发的快捷键」提示，并提供直达设置的入口。
- 状态下拉文案不得出现任何语音输入法的专名。

### 文案与指引

- 现有界面中的豆包专属措辞整体替换为通用语音输入表述，涉及状态播报、设置项标签、按钮映射界面提示等。
- 新增一条配置指引，文案需明确写出：需要到目标语音输入应用自己的设置里，把 `vRemoteDr 2ch` 加入其输入设备列表，否则不会录到声音。**指引中写出确切设备名。**
- 设置项措辞不出现 bundle ID、键码、传输类型等开发者术语。

### 保持不变的部分

- 双麦混合算法、遥控器麦增益、Mac 侧对齐延迟、限幅逻辑，全部不变。
- 虚拟音频驱动及其 `usb` 传输标识不变。该标识是为绕过豆包对 `virtual` 传输类型的过滤而设，Type4Me 很可能不需要，但本次不评估、不改动。
- `vRemoteDr 2ch` 设备名不变。它不含厂商名，且改名会打断用户在别处已保存的输入设备选择，属于对外契约。
- 遥控器按键映射功能不变。
- 新增支持的遥控器型号不在本次范围内。

## Testing Decisions

### 什么算一个好的测试

只断言外部可观察行为：发了什么快捷键、麦克风路由开关的先后顺序、状态文案、错误提示。不断言内部实现细节（私有字段名、调用栈结构、内部数据结构布局）。时间一律通过注入的时钟推进，不使用真实等待。

### 缝 A：会话状态机 —— 复用已有缝，不新增

- **复用现有的语音会话自测装配。** 会话协调器今天已经把它全部协作者以注入契约的形式接收，并配有一组已存在的用例覆盖开麦确认、第二次点击关闭、长按关闭、键盘与遥控器交叉关闭、双遥控器独立停止、去抖重试等行为。
- **替换驱动源，不替换缝。** 现有用例里的假豆包状态提供者被替换为一个假触发器驱动器（模拟语音键按下与抬起），另加一个假占用探针（可控地返回「有人占用 / 无人占用」）。装配代码结构不变。
- **保留并改写既有用例。** 现有断言在 toggle 语义下大部分仍然成立（阶段迁移、触发次数、不重复开麦、跨来源关闭），逐条改写而不是删掉。
- **新增用例覆盖：** 无快捷键配置时语音键不响应且不开麦；占用探针报有占用时关闭被推迟；占用探针报无占用时正常关闭；占用查询排除自身进程；占用判定不会导致无限推迟；尾巴延迟结束后麦克风被释放；两种遥控器在 toggle 语义下仍各自独立；长按与短按在 toggle 语义下分别落在哪个阶段。

### 缝 B：快捷键值 —— 一个纯值类型，最高点开口

这是本次唯一需要新开的缝，理由是现有触发键的投递是一个直接投递到系统事件层的静态方法，无法测试。新缝开在**决策与副作用的交界处**：所有「该发什么」的判断都是纯函数，只有「真的发出去」这一步走可注入发送器。

- **纯函数测试：** 从一组构造出的按键事件描述构建快捷键值；快捷键值渲染回显文本；快捷键值渲染合成事件描述（含键码与修饰标记）。覆盖左右同名键、带主键的组合、双修饰键组合、系统保留键。
- **发送器测试：** 断言 toggle 语义下按下与抬起各投递一次；断言投递次数与语音键按压次数一致（长按不重复触发）。
- **录制交互测试：** 拾取状态下的取消不覆盖已保存值；重新录制覆盖旧值；清除后回到未配置态。

### 缝 C：存量迁移 —— 一个纯函数

- 吃一份设置存储的键值集合，输出迁移决策：迁移 / 视为存量并迁移 / 视为全新安装不迁移。
- 三种情形各一个用例，外加「旧值为无法识别的字符串」的兜底用例。
- **风格照搬仓库现有的无框架自测**：项目已有一份用独立编译方式运行、只包含纯逻辑文件的协议自测，迁移判据是纯逻辑，适合同址同风格扩展，不引入新的测试框架或第三方依赖。

### 不测试的部分

- 真实 CoreAudio 设备枚举、真实系统事件投递、真实 BLE 传输、真实 ATVV 编解码。这些依赖硬件或系统状态，由既有的硬件回归数据与真机验证覆盖，不由自测覆盖。
- 视觉与布局。这由既有的界面约定与真机走查覆盖。

## Further Notes

**验证过的事实（决定了本方案的形态）：**

- 目标语音输入应用支持在设置里按优先级指定多个输入设备，最后回退到系统默认。因此「用户在目标应用里选择 `vRemoteDr 2ch`」这一步是可行的，音频交付通路无需改动。
- 遥控器麦克风的打开是 vRemoter 通过遥控器私有协议主动发起的，与目标应用无关。因此会话生命周期完全可以由 vRemoter 自行持有。
- 「无需指定目标应用、由 vRemoter 自己持有 toggle 状态机」与「关闭前做占用检查兜底」这两个决策置信度并不高（分别为 0.48 与 0.51），是四选一与四选一里勉强领先的结果。其中第二项最终选定设备占用检查而非固定延迟尾巴，理由是机制层面：固定延迟只在目标应用正常收尾时有效，若第二次快捷键被吞掉，目标仍在活跃录音，尾巴只是把失败推迟。而设备占用检查直接测量「是否还有程序在读这个设备」，是唯一真正堵住该失败模式的手段。尾巴延迟被保留为补充。

**需要用户执行、应用无法代劳的一步：**

目标语音输入应用需要用户亲自在其设置里把 `vRemoteDr 2ch` 加入输入设备列表。这一步无法由 vRemoter 代劳（各应用的设置机制不同，且 vRemoter 无权修改他人配置）。如果界面不明确写出这一步，用户会遇到「vRemoter 配好了、遥控器也在录音、但目标应用录到静音」的现象——这是本功能上线后最可能被误报为 bug 的情况，指引文案必须显眼。

**已知的遗留问题（非本次引入，本次不修）：**

- 界面中仍存在大量调试性质的文案与开发者术语，与本次「文案去豆包化」的目标部分重叠。本次只处理与语音目标、触发键相关的部分，其余按外科手术原则不顺带整理。
